# 十條不變量：換掉任何一條，玩起來就不是 GROW 了

什麼時候讀：開工前、或使用者提出的點子可能碰到下面某一條時（例如「加個提示泡泡」「讓玩家悔棋」「兩條路都算贏」）。
碰到時不要默默照做，也不要默默拒絕：指出是哪一條，說明代價，請使用者裁決。

這十條萃取自 Eyezmaze 的 GROW 系列（GROW Island／Cube／Valley）的玩法分析，以及作者先前做的一款 GROW 式遊戲（下稱「原作」：8 個物品、唯一正解、多個壞結局）。
例子用 dragon-valley 範例（農田、神殿、巨龍……），只是說明，不是規定。

---

## A1. 一組固定物品，每個放一次，放的順序就是玩家唯一的輸入

沒有悔棋、沒有其他操作、沒有亂數。N 個物品就是 N! 種局（8 個 = 40,320 種），每種的結果完全由順序決定。隨時可以 RESET 重來，但不能退一步。

- 實作上：`place(state, id)` 是純函數；求解器才能全枚舉。

## A2. 每回合放一個，然後場上「所有已經放下的東西」照規則各自長一步，長的過程會互相帶動

升級的常常不是剛放的那個：放下的物品常常只是觸發器，戲演在別人身上。已經放下的每個東西各自變一次身，一次一個、一個 LEVEL UP、本體明顯變形。

## A3. 等級是唯一的回饋，全部 MAX 才是真結局

每個物品有 Lv 和 MAX；全部到 MAX 才是真結局，其他都是壞結局或「再接再厲」。等級是玩家唯一的回饋，也是解謎的線索。

## A4. 只有一條（或極少數）路能全滿；其他順序要看得出「長不全」

GROW 系列只有一條正解，其他順序明顯長不全。原作從「剛好兩條正解、兩個真結局」改成「剛好一條」，就是為了這一點：兩條正解時，玩家看不出自己錯在哪。

- 驗法：`ACCEPTANCE.trueEndings: 1`，`npm run check` 全枚舉。

## A5. 線索只來自看得到的狀態，不用任何文字或提示

玩家推順序靠四件事：

1. 級數多寡：級數少的晚放。
2. 哪個東西停下來不長。
3. 哪一回合有東西一口氣長兩級。
4. 壞結局的畫面。

不加文字或泡泡提示。

## A6. 因果看得見，失敗也讀得懂

放了 X 就看得到 Y 因它而長；壞掉的東西會拖垮依賴它的東西，結算時一排低等級都指向同一個問題。GROW 的失敗好讀，正是因為壞掉的東西會連鎖。

- 規則層的對應：連鎖樞紐（[choices.md](choices.md) 的「連鎖」）、災害鎖住、搗蛋守門口。
- 注意：原作一度把這條推到「每一級都要觸發者」，後來推翻。留下來的是「因果看得見」，不是「每一級都要等人」：自己長的級數可以有（[choices.md](choices.md) 的 B8、B-X3）。

## A7. 無字：由場景本身說故事

畫面上的字只剩 LEVEL UP（有降級才有 LEVEL DOWN），加上 UI 上的等級數字。泡泡只有符號和圖，沒有文字。

- 規則層的 `STORIES` 與條件註解只給除錯、劇透表、求解器輸出用，不上畫面。

## A8. 一回合是一條主線、一次只有一個主角，結果出現在主角停下的地方

主角走過去、做一件事、結果長在那裡；LEVEL UP 只標在被升級的東西頭上；每次升級留下一個會動的東西。這是 GROW 三款共通的演出規則。

- 這是演出層的事，規則層要提供的是 `grow` 事件的 `via`（真的讓條件成立的幫手），演出才知道「誰走去誰那裡」。見 [presentation.md](presentation.md)。

## A9. 全部放完之後有一段收尾考驗，每個結局有自己的畫面

GROW Island 最後是火箭上月球或 UFO 來訪；dragon-valley 是魔王來襲。考驗的結果由最終狀態決定；每個結局有自己的畫面，也就是截圖點和重玩動機。

- 規則層的對應：`FINALE`（有序清單，第一個成立的就是結果）與 `ENDINGS`。
- 考驗不一定要在全部放完之後才來：大綱的考驗本身就是玩家放下的物品時（流星雨、怪獸），它是順序裡的災害物品，`FINALE` 省略；這一條守住的是「最後有收尾、每個結局有自己的畫面」，收尾畫面照 `resolve().id` 挑。

## A10. 製作上的不變量：規則是純資料，可以全排列驗證

引擎、求解器、演出層共用同一份規則表；每次改規則都要全枚舉，驗「走到真結局的順序剛好 1 條」。不能驗證就不知道還是不是 GROW。

- starter 的 `npm run check` 就是這一條。
