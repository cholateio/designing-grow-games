# 元件選單：原作的選擇，照元件分組

什麼時候讀：流程第 2–4 步（定尺度、挑元件、寫規則資料）；以及使用者想加或拿掉某種機制時。

「原作」指這個 skill 萃取自的那款 GROW 式遊戲（作者先前做的，8 個物品、唯一正解、多個壞結局）。這裡的每一條都是 **原作的選擇，不是規定**。格式：

- **決定**：原作怎麼做（用抽象的說法或 dragon-valley 的例子說明）。
- **為什麼**：當時的理由。
- **可調性**：新專案什麼時候該改、怎麼改。

每組開頭有一句「不用這個元件的代價」，挑元件時拿它跟使用者的大綱對照。每組最後列出原作在這個元件上**試過又拿掉的做法**（編號 B-Xn），新專案預設不要做；要做先跟使用者講清楚代價。
`starter` 欄位與 `dragon-valley` 範例的對應寫在每組的「starter」一行。

---

## 尺度（物品數、回合數、級數分層）

不用這個元件的代價：不先算可行性就定級數，很可能沒有任何順序能全滿（原作第一版就是），之後只能砍級數或加回合重來。

starter：`ORDER`（長度 N）、`CLOSING_TURNS`、`ITEMS[id].max`。dragon-valley：6 個物品、`CLOSING_TURNS` 1、最高級 9／7／6／5／3／3。

**B1. 8 個物品、9 回合（8 次放置 + 最後一輪 `CLOSING_TURNS = 1`）。**
- 為什麼：原本是 8 次放置加倒數 3 回合自動長。看過實際錄影後拿掉了：全部放完後大家一起自動升級，不是玩家的選擇造成的，違背 GROW「選擇導致升級」的主旨。後來改唯一正解時，也決定不加到 10 回合來湊。
- 可調性：物品數決定 N!（6 個 720 種、7 個 5,040、8 個 40,320、9 個 362,880——starter 的 `npm run check` 8 個約 1 秒，9 個約 10 秒（視機器），10 個開始不實際）。回合數決定第 k 個放的最多能長幾級（見 B2）。

**B2. 級數分層：最高級依「該第幾個放」來定。**
- 決定：早放的級數高、晚放的級數低，依序遞減。例：dragon-valley 照正解位置是 9／7／6／5／3／3。
- 為什麼：分層讓每一樣都到得了 MAX，同時是推理線索：級數少的晚放。
- 可行性算式：總回合數 T = N + `CLOSING_TURNS`；第 k 個放的，不跳級最多到 **T − k + 2** 級（放下當回合可到 Lv2，之後每回合 +1）；每用一次跳級多 1 級；`up[2]` 要 `age ≥ 1` 的物品（放下當回合不長）少 1 級。T = 9 時是 11 − k；dragon-valley T = 7：9 − k。
- 審稿曾發現第一版「沒有任何順序能全滿」：第 8 個放的只有 3 個成長回合。當時選擇分層，不選連跳。
- 可調性：分層的形狀自由，但正解上每一樣都要到得了 MAX。先把可行性表填進 `templates/rules-design.md`，再寫內容。總級數改了幾次都沒關係，每次都先重算可行性表。

被拒絕的做法：
- **B-X17. 加回合來湊可行性。** 可行性不夠時先調分層與跳級，回合數是使用者的決定。

## 成長節奏（每回合怎麼長、條件怎麼寫）

不用這個元件的代價：沒有「每回合一步、+2 上限」與「條件從正解回推」，錯的順序也會一路長到 MAX，唯一解與可讀性一起消失。

starter：引擎內建（每回合一步、+2 上限、剛放下最多到 Lv2、knocked、掃描順序）；`ITEMS[id].up`、條件語言。

**B3. 每回合每個物品只走一步：+1 或跳級 +2；一回合最多比回合開始高 2 級，事件帶來的加減也算在內。**
- 為什麼：不讓任何東西放下去就連跳到 MAX；連跳幾級的動畫也會太長。
- 可調性：引擎行為，starter 固定。要改得改引擎並重寫測試；不建議。

**B4. 剛放下的物品當回合就參加升級，最多到 Lv2。**
- 為什麼：玩家要看得出「因為我現在放了 X」。實測不讓它當回合長，總級數就排不下。
- 可調性：個別物品想要「放下當回合不長」，就把它的 `up[2]` 寫成 `{ age: [id, 1] }`（dragon-valley 的巨龍就這樣）。

**B7. 固定的掃描順序，反覆掃到不動為止，掃到誰就當場決定。**
- 為什麼：引擎要確定性（同一順序永遠同一結果），同回合的連鎖也要能發生；「當場決定」讓結果不依賴「等一下會不會跳級」的預判。
- 決定：`ORDER` 是物品清單兼掃描順序（原作的跟正解順序不同）。+1 不會為了等跳級而延後；同回合「A 升了讓 B 升」照樣成立。
- 後果：排在前面的物品第一輪看到的是別人還沒升的級數。`up` 裡「至少」類的條件（`minLevel`、`present`）每一輪都重看，不受影響；在發生那一刻只判定一次的事（跳級的決定、`fx`／`onLevel` 的 `when`、`branch.when`、正向 `delta`）和會在同一回合由真變假的條件（`maxLevel`、`not`、`ltPlus`、`flag … is`）會受影響——dragon-valley 騎士的分岔就靠法師排在騎士前面。細節與怎麼刻意利用：[process.md](process.md#掃描順序-order同一回合誰先看到誰)。
- 可調性：`ORDER` 是隱藏的設計參數，換順序可能改變解。改了就重跑 `npm run check`。

**B8. 每一級的條件從正解回推：正解上那一回合場上有什麼，就要求什麼。**
- 例：dragon-valley 神殿 3→5 的跳級要騎士在場、農田 ≥5、法師 ≥2，正解第 4 回合正是如此。
- 為什麼：要剛好一條全滿；錯的順序會在這些格停下來。
- 結果：原作最後的表大約八成的升級帶條件，其餘自己長（`{ always: true }`），另有約十條跳級。這推翻了更早定的反目標「阻擋＋跳級合計超過 20 條就是走回頭路」；矛盾靠「失敗看得見」補（災害、連鎖、搗蛋、壞結局），條件本身不演出。dragon-valley 27 個升級裡 24 個看別的物品。
- 可調性：「從正解回推」是寫條件的方法，不是「每一級都要有條件」（那是被拒絕的 B-X3）；自己長的級數完全可以有。要寫幾條是難度與可讀性的選擇：條件多，隨機平均 MAX 低、失敗連鎖得看得懂；條件少，表穩、好調，但錯的順序也長得高。物品少（6 個以下）時，級數分層加一兩條跳級本身就可能擋出唯一解，條件主要用來壓平均 MAX、讓失敗看得懂（dragon-valley 就是這樣，見 [process.md](process.md#4-唯一性從哪裡來)）。條件數量要不要設上限，拿 `npm run check` 的數字跟使用者講好（見 C21）。

**B9. 每一條條件都要說得出故事：誰來了、誰夠高了。**
- 為什麼：玩家推理靠故事；這是「每一級都要觸發者」那批設計被推翻之後，唯一留下來的原則。
- 例：dragon-valley「法師塔要磨坊有餘糧（農田 ≥5）」「農田要神殿的祭司來祈福」。
- 故事寫在 spec 的註解和 `STORIES`，畫面上不印。
- 可調性：強烈建議保留；要改先問使用者。說不出故事的條件，玩家就沒有東西可以推理，通常就是該拿掉的條件。

**B10. 條件語言。**
- 為什麼：條件全是資料（不是函式），求解器才能全枚舉、結構檢查才能抓打錯的物品名，引擎也才能從條件找出 `via`（幫手）給演出層。
- 原語：`always`、`present`、`absent`、`minLevel`、`maxLevel`、`ltPlus`、`age`、`flag`（含 `is`）、`locked`、`and`、`or`、`not`；另有 `allMax`、`finale`（結局用）。`maxLevel` 是絕對語意：還沒放的 0 也算 ≤n。說明在 starter 的 `spec.template.js`。
- 可調性：要新原語就改 `rules/conditions.js` 並補 `validate.js`、測試。

**B11. 時間窗口條件（「要趕在某事之前」）用 `maxLevel` 寫。**
- 為什麼：「趕在某事之前」是最典型的順序線索（早放才來得及），只用 `minLevel` 寫不出來。
- 例：「A 的第 3 級要在 B 還 ≤k 的時候動工（趕在 B 擴建、把地占走之前）」。窗口門檻一開始常常設得太緊，要靠求解器逼著放寬才有解。
- 可調性：窗口門檻常常要靠求解器調；調的時候故事跟著改。

**B16. 這回合被降級的物品，這回合不再升級（knocked）。**
- 為什麼：同一回合先 LEVEL DOWN 又 LEVEL UP，玩家讀不出發生了什麼。壓在 Lv1、沒真的掉級也算。
- 可調性：引擎行為，starter 固定。

被拒絕的做法：
- **B-X3. 每一級都要有觸發者（Lv3 以上沒有自己長的）。** 起因是把「GROW 的『不升級』可以參考」推廣到每一級；「可以參考」不等於套到每一級。整批重做。
- **B-X8. 全部放完後自動長幾回合的蒙太奇加倒數 3-2-1。** 考驗警告之後突然大家一起升級、動畫又快，看起來很怪，也不是選擇造成的升級。
- **B-X13. 同一回合 LEVEL DOWN 又 LEVEL UP。** 見 B16。

## 跳級（一回合 +2）

不用這個元件的代價：完全沒有跳級時，第 k 個放的只能到 T − k + 2 級，分層很難排得下、也少了「一口氣長兩級」這條玩家看得到的線索；但跳級太多比沒有更糟（見 B-X2）。

starter：`ITEMS[id].jump[n]`（在 n−2 時成立就一回合 +2）。dragon-valley：農田 `jump[5]`、神殿 `jump[5]` 兩條。

**B5. 沒有預設跳級：只有 spec 寫的 `jump[n]` 會跳，而且只留正解需要的（原作只有約十條）。**
- 為什麼：試過「每一級預設可跳」，最後幾回合一回合長 9–11 級、錯的順序也有七個 MAX，因此否決。跳級本身是線索：「因為 X 來了，一口氣兩級」，錯的順序跳不起來，就差一兩級到不了 MAX。
- 可調性：條數照可行性需要定，越少越好；每一條都要有故事。

**B6. 跳級是捷徑：從 n−2 直接到 n，不看 `up[n−1]`。所以任何阻擋都要同時寫進會跨過它的跳級。**
- 為什麼：跳級的意思就是一回合 +2；如果還要看 `up[n−1]`，跳級就只是兩次 +1，「因為 X 來了一口氣兩級」這條線索就沒了。
- 例：dragon-valley 神殿 `jump[5]` 帶著跨過的 `up[4]` 的「法師 ≥2」。漏寫的話，錯的順序可以靠跳級繞過本來該擋住它的條件，失敗的連鎖就被跳過去了。
- 可調性：這是 starter 引擎的語意（要讓跳級也看 `up[n−1]` 得改引擎，而且「一口氣兩級」的線索會變弱）。照現在的引擎，寫完跳級就回頭對一次 `up[n−1]`。

被拒絕的做法：
- **B-X2. 每一級預設都能跳級（`up[n−1] ∧ up[n]`）。** 最後幾回合一回合 9–11 級、錯的順序也有 7 個 MAX、讀不出來。
- **B-X23. 跳級時連冒兩個 LEVEL UP。** 改成冒一個大一號的。

## 災害（放下那回合一次檢查、期間持續有效、鎖住）

不用這個元件的代價：錯的順序只會「長得慢一點」，沒有一眼看得出的失敗瞬間，也少了「這個要趕在災害前長到某級」這條最強的順序線索。

starter：災害物品的 `fx`（放下時的檢查，`lock` + `flag`）＋ `hazard: { while }`（期間內才放下的 X 當場套用 `fx` 裡 `lock === X` 的那條）。dragon-valley：巨龍（農田 ≤1 燒光、神殿 ≤1 掃倒；Lv1–2 期間持續）。

**B12. 災害物品放下那一回合就把所有檢查一次做完，之後持續一兩回合再結束。**
- 決定：放下時檢查幾個物品，「還太低 → 鎖住並立壞結局旗標」；也可以有「只立旗標、不鎖」的檢查。dragon-valley 的巨龍：農田 ≤1 燒光、神殿 ≤1 掃倒，Lv1–2 還在谷裡、Lv3 回巢。
- 為什麼：最早的版本是災害一回合移動一站、逐格影響，4 級；玩家看不出它什麼時候打到誰。改成「放下當下全場檢查、太初階的直接壞掉、之後不再升級」，失敗的瞬間就只有一個、很好讀，災害本身也縮短了。
- 可調性：檢查幾項、門檻多少都可調；門檻要能讓每個災害結局都當得上標題（`npm run check` 的 `badUnreachable` 與 stats 的分佈）。

**B13. 災害持續有效：在災害 Lv1–2 期間才放下的東西，當場套用對它的那一條檢查。**
- 為什麼：玩家會自然期待——在災害還在的時候才放下的東西，沒受到影響反而奇怪（原作的試玩者第一個問的就是這個）。看的是回合開始時的災害級數。
- 副作用：原作的正解因此換了順序。
- dragon-valley 的 `expected.js` 用 `NOTABLE` 釘了一條示範順序（巨龍還在谷裡時才放神殿 → 當回合被掃倒）。
- 可調性：強烈建議保留。不要的話就別寫 `hazard`。

**B14. 被鎖的物品永遠不再長；鎖住時立的旗標直接就是壞結局。**
- 為什麼：鎖住是最好讀的失敗：那一格從此停住，結算時一眼看得到；同一個旗標又直接當結局判定，規則與畫面不會對不上。
- 演出：鏡頭到被鎖的那一格、套用、≤ 1.5 s，不冒字。演出層用 `lockFlags(spec)` 讀哪些旗標是鎖。
- 可調性：可以有「只立旗標不鎖」的檢查，但鎖住的那種最好讀。

**B17. 災害不降級：只鎖住它打到的那一樣，不連帶扣別人的級數。**
- 為什麼：災害讓旁邊無關的東西降級，玩家讀不出兩者的關係，只覺得被懲罰。
- 可調性：要不要有降級是使用者的裁決（SKILL.md 的「一定要問」）。

**B21. 唯一解被規則改動打破時，用有故事的門檻調整救回來。**
- 為什麼：門檻的數字玩家看不到，故事才是玩家推理的對象；數字改了故事跟著改，條件才不會變成「為了湊解而存在」。
- 做法：規則改動（例如加上 B13 的災害持續）讓解變成零條或多條時，先找一條災害檢查或窗口條件，收緊或放寬它的門檻，同時換一個說得通的故事。例：dragon-valley 的巨龍門檻調過三輪（≤3／≤2 → ≤1／≤1），故事改成「乾草田一點就著、水田不怕火」。
- 可調性：見 [process.md](process.md) 的救回唯一解階梯。

被拒絕的做法：
- **B-X12. 災害讓無關的東西降級。** 見 B17。
- **B-X18. 災害一回合移一站、逐格影響，而且一直持續到最後。** 改成觸發器：三級、放下那回合全部檢查。

## 搗蛋（抓住目標直到離開窗口）

不用這個元件的代價：晚放的低級物品只是「最後補上」，沒有自己的戲；早放也沒有懲罰，順序線索少一條，演出層也少了一個「出問題指標」角色。

starter：`grip: { while, targets, story }`（期間內才放下的 targets 被抓住，旗標 `gripped_<id>`，`grippedBy()`）、反應的 `grip: true`（搭配 `delta`）。dragon-valley：哥布林 Lv1–2 占住之後才放的農田／神殿，騎士團收編（Lv3）才放開。

**B15. 搗蛋物品會抓住東西，被抓住的停住，直到搗蛋物品離開窗口。**
- 決定：有兩種抓法可以單用或並用：放下時抓住已經在場、還太低的目標（反應的 `grip: true`，可以搭配負向 `delta`）；搗蛋物品在窗口期間才放下的目標當場被抓住（`grip` 區塊）。被抓住的在搗蛋物品離開窗口之前都不長。dragon-valley：哥布林 Lv1–2 占住，騎士團收編（Lv3）才放開。
- 為什麼：跟災害持續一樣，玩家會期待「它還在場時才放下的東西也會被搗亂」；被搗亂之後下一回合自己恢復，則讓人覺得不合理，所以抓住要一直持續到它離開。
- 引擎細節：這回合就會離開窗口就不抓（先「不抓」試跑一次）；一個物品只被第一個抓它的抓住。
- 可以接受的後果：搗蛋物品早放又抓到，目標可能永遠卡住；這可以當成「設計上的壞路」接受，但要用 `npm run stats` 看它佔多少順序。dragon-valley 的哥布林放第 1 個就是這樣。
- 可調性：targets、窗口長短可調；離開窗口的條件最好依賴別的物品（哥布林被騎士收編），才會變成順序線索。

**B35. 搗蛋角色兼當「出問題指標」。**
- 為什麼：失敗原因要無字地指出來；撲空、拜訪這類演出都拿掉之後，搗蛋角色本來就在場上跑，順便指路最不突兀。
- 決定：搗蛋角色（Lv1–2）每回合跑去第一個被鎖或在等幫手的物品門口晃，取代文字或撲空演出。
- 可調性：演出層的事；規則層提供 `wait` 事件（誰在等誰）。

被拒絕的做法：
- **B-X21. 角色太多、搗蛋角色太多。** 畫面一亂，玩家就找不到主角；搗蛋角色前期一兩隻就夠，後期再減少。

## 連鎖（樞紐）

不用這個元件的代價：一個東西壞了，其他照樣長到 MAX，看起來「差一點」；失敗的原因散在各處讀不出來，隨機平均 MAX 也偏高。

starter：沒有專用欄位——就是很多條件都寫上同一個物品的級數。dragon-valley：神殿（農田 4／7／9、法師 2／5、騎士 2／3／5 都要神殿夠高）。

**B18. 連鎖：靠某個樞紐的級數，條件裡都寫上那個樞紐。樞紐壞了，依賴它的全部跟著停。**
- 為什麼：原作一度在樞紐壞掉之後，全場照樣長到接近全滿，看起來像只差一點。改法：讓很多物品的條件都寫上樞紐。效果：同一局結算變成一排低等級，全指向樞紐；隨機平均 MAX 也明顯下降。當時選連鎖，不選「壞結局一觸發全場停止」。
- 可調性：樞紐最好就是災害會打到的那個物品，失敗才連得起來。注意跳級（B6）不要繞過樞紐。

**B22. 死規則不留。**
- 為什麼：死規則會誤導讀規則的人（設計者、演出層），而且常常是某次改動之後悄悄失效的訊號。
- 例：一條反應在別處的條件改了之後永遠成立不了，拿掉；一個壞結局在全部順序裡一次都當不了標題，整條拿掉。
- 可調性：強烈建議保留；要留死規則（例如預留給下一版）先問使用者並記帳。`npm run check` 的報告會列出死規則（從未成立的條件、從未發出的反應、從未立過的旗標）。

## 分岔（某一級看別人決定最終型態）

不用這個元件的代價：真結局只是「全 MAX」，少了「全 MAX 還不夠、還要在對的時機」這一層，正解的最後幾步比較容易被試出來。

starter：反應的 `branch: { flag, when, then, else }`，放在 `onLevel[n]`；真結局的 `when` 寫 `and({ allMax: true }, { flag, is })`。dragon-valley：騎士 Lv5 看法師 ≥6 → 聖騎士，否則黑騎士。

**B19. 分岔旗標：某一級看另一個物品的級數，決定最終型態。**
- 決定：例：dragon-valley 騎士升到最終級（5）時看法師：法師已經 ≥6 → 聖騎士（真結局的條件）；否則黑騎士（一個壞結局）。
- 為什麼：原本兩個分岔各是一個真結局；改唯一正解後，另一支變成壞結局，畫面保留。
- 可調性：守著不變量 4（一條正解）時，分岔的另一支就是壞結局；兩支都當好結局等於兩條正解（B-X1 被拒絕過），要這樣做先問使用者。

被拒絕的做法：
- **B-X1. 兩條正解、兩個真結局（分岔路線）。** GROW 只有一條正解；兩條正解加上到處跳級，玩家「錯在哪看不出來」。

## 過期（放太久還不夠高）

不用這個元件的代價：最早放的物品沒有時間壓力，「這個要早放」的線索只剩級數分層一條；也少了一種跟災害無關的壞結局。

starter：`AFTER_TURN`（回合結束的反應）＋ `age`、`maxLevel` 條件。dragon-valley：農田開墾 4 回合還 ≤4 → 饑荒。

**B20. 過期旗標：回合結束時檢查。**
- 為什麼：給最早放的物品一個時間壓力，「要早放、而且要有人幫它長」就成了線索；也多一種跟災害無關的壞結局。
- 決定：過期規則多半放在早放的物品上，門檻要在正解上剛好不觸發（正解那條路上它剛好長得夠快）。dragon-valley：農田開墾 4 回合還 ≤4 → 饑荒。
- 可調性：門檻要讓這個結局當得上標題——它常被前面的災害結局遮住（dragon-valley 第一版的饑荒 satisfied 305、resolve 0）。看 stats 的分佈調。

## 收尾考驗（全部放完之後的考驗）

不用這個元件的代價：最後一回合就直接結算，沒有高潮、沒有「各結局自己的畫面」的掛點，壞結局也只能靠旗標區分。

starter：`FINALE`（有序 `[{ id, when }]`，第一個成立的就是結果；**可省略**）；`ENDINGS` 用 `{ finale: id }` 讀它；`resolve()` 回傳 `finale`（沒有 `FINALE` 時是 `null`）。dragon-valley：魔王來襲（神殿 MAX 擋下／巨龍還在谷裡趕走魔王／命中）。

什麼時候不用 `FINALE`：大綱的「考驗」本身就是玩家放下的物品（例：太空站大綱的一場流星雨）。這時把它做成災害物品放進順序（放下那回合檢查、期間持續），它放在第幾個就是謎題的一部分；`FINALE` 省略或寫 `[]`，結局全靠旗標與 `allMax` 判定，演出層照 `resolve().id` 挑收尾畫面。上面那條「不用的代價」由各結局自己的收尾畫面補上。劇透表的統計會寫「沒有 FINALE」。

**B24. 收尾考驗的結果由最終狀態決定，有兩三種就夠。**
- 決定：有序清單、第一個成立的就是結果。例：dragon-valley 的魔王來襲：神殿 MAX → 結界擋下；否則巨龍還在谷裡 → 把魔王趕走；否則命中。
- 為什麼：考驗把整局的狀態收成一個看得見的高潮；每種結果都要讓玩家看得出「是哪個東西不夠」。語氣：避免可能被讀成影射真實衝突的造型；全程卡通、沒有火與廢墟，擋下像放煙火，沒擋下像卡通被撞扁。
- 可調性：結果種類可多可少。**同一個結局可能對應不同的考驗結果**（dragon-valley 的「結界未成」包含命中與被龍趕走兩種）：結局的 `line` 只寫兩種都成立的事，演出層照 `finale` 挑畫面。

**B28. 能力只在真的有效的那一級才畫出來。**
- 決定：能力只在真的有效的那一級才畫出來；還沒有效的級數畫成「施工中」之類的樣子。
- 為什麼：能力看起來已經有了，關鍵時刻卻沒發揮、又沒有解釋，玩家會覺得不合理。
- 可調性：強烈建議保留；要改先問使用者。原則：擋下考驗的東西，在擋得下的那一級才出現。

被拒絕的做法：
- **B-X15. 看起來有了、其實沒用的能力。** 見 B28。

## 結局（判定清單、收尾畫面、圖鑑）

不用這個元件的代價：只有「成功／失敗」兩種結局時，失敗不告訴玩家錯在哪，也沒有重玩動機；壞結局不分開排序時，同一張圖佔掉大部分的局（原作一度如此）。

starter：`ENDINGS`（有序 `[{ id, title, kind, when, line? }]`，恰一個 `true`、恰一個 `neutral`）；`satisfied()`、`resolve()`。dragon-valley：1 真、5 壞、1 neutral。

**B23. 只有一個真結局；判定用一張有順序的清單。**
- 為什麼：一局只能演一個收尾；有順序的清單讓「玩家看到哪個」可以預測、可以用求解器量。
- 決定：真結局 = 全 MAX 且分岔走對。否則清單裡第一個成立的壞結局當標題，其餘列附註；都不成立是 neutral（「再試一次」）。順序：具體災難排前面，「考驗沒擋下」排最後。
- 可調性：清單順序決定哪個結局當標題，改順序就改分佈。

**B25. 每個壞結局都有自己的收尾畫面；收尾清單放在規則層。**
- 為什麼：原作一度大多數的局結尾都是同一個畫面，玩家覺得壞結局只有一個。之後各結局補上自己的收尾，各 ≤ 7 s。
- 可調性：壞結局數量是使用者的裁決；每多一個就多一段收尾要做。

**B26. 只有一種順序到得了、又不是全 MAX 的結局，拿掉。**
- 為什麼：只有一條順序到得了的非真結局，玩家幾乎不可能看到，卻要多做一段收尾、多佔一格圖鑑。neutral 留著當安全網，但不進圖鑑。
- 可調性：`npm run check` 的「單一順序結局」報告會列出來，拿去問使用者。

**B27. 結局要看得懂，而且只演標題講的那件事；不噁心，也不違背物品自己的故事。**
- 為什麼：結局畫面是玩家理解「錯在哪」的最後一個管道，也是截圖點；看不懂或讓人不舒服，前面的規則設計都白費。
- 例：原作有一個結局畫面改了三版：太滿讓人不舒服 → 太少看不出來 → 只演出事的那一區。
- 可調性：強烈建議保留（尺度與語氣的界線由使用者定）；做法是在手機截圖上迭代。

**B29. 結局圖鑑：記在本機，只記最後判定的結局，沒看過的格子是「？」。**
- 為什麼：結局分得開之後，收集結局就是重玩動機；用圖示不用文字描述，守住「無字」。
- 歷史：原作一開始因為不想給結局文字描述而不做圖鑑，後來改成只有圖示的版本才加上。
- 可調性：UI 的事，新專案自己決定。

被拒絕的做法：
- **B-X11. 噁心或違背物品故事的大場面。** 見 B27。
- **B-X16. 只有一種順序到得了、又不是全 MAX 的結局；永遠當不了標題的結局旗標。** 見 B26、B22。

## 難度數字（驗收門檻與分佈）

不用這個元件的代價：不量就不知道難度——原作隨機玩平均不到 1 個 MAX，是很硬的謎題；沒有數字就沒辦法跟使用者討論「要不要這麼難」。

starter：`ACCEPTANCE`（`trueEndings`、`everyBadReachable`、`maxAvgMax`、`minMaxTurns`、`greedyMustFail`、`custom`）；`npm run check` 的分佈與報告。

**B31. 難度門檻（驗收）。**
- 為什麼：每一條都對應一個踩過的坑：多解（錯在哪看不出來）、到不了的結局、太簡單（隨便放都有好幾個 MAX）、貪婪就破關、MAX 全擠在最後一回合。
- 決定：全滿的順序剛好 1 條且是真結局；每種壞結局至少一個順序成立；一條主題專屬的檢查（寫成 `custom`）；隨機平均 MAX ≤ 3.5；貪婪策略走不到真結局；正解至少 2 個回合出現 MAX；引擎不出錯。
- 可調性：`maxAvgMax` 與最大宗結局佔比是**使用者的難度裁決**，不要自己訂。先跑一次看實測值，再拿數字去問。

**B32. 每次改規則都記下分佈。**
- 為什麼：分佈是難度與「結局分不分得開」唯一量得到的證據；寫下來才看得出每次改動的影響。
- 記什麼：全 MAX 幾條、每個結局幾條（resolve）、MAX 數分佈與平均。格式看 dragon-valley 規則表的檔頭。
- 原作的觀察：隨機平均 MAX 隨著加連鎖、定唯一正解、加災害持續一路往下掉，最後不到 1。這是觀察，不是裁決——新專案要決定能不能接受。
- 可調性：每次改規則都把分佈寫回 spec 的註解。

**B33. 正解逐回合表（含每個升級是被誰帶動的 `via`）要留著當設計的權威。**
- 為什麼：逐回合表是規則（條件從它回推）、演出（分鏡）、測試（代表順序）共同的參照；改規則先改它。
- 決定：正解每回合 ≤ 8 個升級事件（跳級算一個），最後一回合最多。
- 可調性：`npm run solutions` 產生；事件數上限跟演出時間有關，跟使用者講好。

**C21. 用反目標的數字當警報，但要承認被推翻過。**
- 為什麼：反目標無聲失效，等於沒人知道還要不要守它。
- 原作的反目標「阻擋 + 跳級 ≤ 20」，在唯一正解之後實際是兩倍多，卻沒人重新裁決。
- 可調性：新專案要嘛把反目標寫進 `ACCEPTANCE.custom`，要嘛明文作廢。

## 可讀性（不用字也看得懂）

不用這個元件的代價：規則對了、玩家還是讀不出來——原作大部分的返工都在這一組；做錯的典型是加提示、加字、加強調動畫，最後全部拿掉。

starter：規則層只負責提供資料（`grow` 的 `via`、`wait`、`lock`、`STORIES`）；畫面怎麼做見 [presentation.md](presentation.md)。

**B30. 中央地標是全場進度計，不是物品。**
- 為什麼：全場總等級給玩家一個「整體進度」的感覺，又不用文字。
- 決定：階段由所有物品等級總和決定，回合最後才結算；門檻取在正解總等級曲線的空檔。階段名文字後來拿掉。
- 可調性：可有可無；有的話它是演出層算的，不進規則表。

**B34. 物品卡住時，畫面上照樣長（虛構的級數）：只在演出層，不動求解器。**
- 為什麼：早放卻等不到幫手的物品，畫面會停著好幾回合；讓它在畫面上自己多長一兩級（虛構、不冒 LEVEL UP），畫面才有在動。被鎖的改成壞掉的樣子。
- 可調性：要做哪些物品由使用者決定（原作只做了一樣）。

**B36. 物品列每回合結束寫上 Lv.n，MAX 變色；有放置順序徽章。**
- 為什麼：GROW 只在結局亮出等級，原作刻意偏離：解謎線索比忠於 GROW 重要。
- 可調性：UI 的事；值得保留。

**B37. 主題與語氣的硬限制。**
- 為什麼：搞笑題材很容易踩到真人與政治；原作改過兩次，兩次都是做完才發現。
- 決定：「惡搞但溫柔」，不影射真人或政黨；避免可能被讀成影射真實衝突的元素（旗幟、武器這類）。
- 可調性：語氣禁區是使用者的裁決（SKILL.md 的「一定要問」）。

被拒絕的做法（全部是「用演出補提示」，新專案預設不要做）：
- **B-X4. 拜訪演出（幫手走過去敲門再升級）。** 畫面上看起來只是有個角色突然出現、點兩下頭，物品就升級了，讀不出因果。
- **B-X5. 撲空演出（等不到幫手的人走過去、低頭嘆氣）。** 看不出意義。
- **B-X6. 起因提示（升級前鏡頭先去幫手那棟，讓它閃一下或彈一下）。** 連「彈一下」都嫌多，相關程式整個刪掉。
- **B-X7. 任何泡泡或圖框形式的提示。** GROW 不給提示，這點重申過兩次。
- **B-X9. 畫面上的說明字、標題字、階段名、跑馬燈、結局標題卡。** 遊戲裡的小字越少越好。
- **B-X10. 建築變白、發光、原地縮放彈出。** 原地縮放看起來不自然；純白閃讀成故障。
- **B-X14. 小孩隨等級放大。**
- **B-X19. 同一件事拆成兩段動畫。** 多餘。
- **B-X20. 用加速來縮短回合。** 留主意、砍停頓，不加速。
- **B-X22. 跟主線無關、看不出意義的點綴角色或建築。**
- **B-X24. 鏡頭不動、讓玩家自己找事件在哪。** 改成鏡頭跟著主線走。
- **B-X25. 起因光點、轉頭這類因果視覺化。** 畫面太亂。
