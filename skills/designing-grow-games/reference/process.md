# 流程與工具：規則怎麼驗、什麼壞過、怎麼救

什麼時候讀：流程第 4–7 步（寫規則資料、全枚舉驗證、救回唯一解、釘代表順序）；`npm run check` 失敗或報告看不懂時；要改引擎時。

starter 的檔案路徑都相對於複製出來的 starter 資料夾。「原作」指這個 skill 萃取自的那款 GROW 式遊戲（作者先前做的，8 個物品）。

---

## 1. 規則是純資料，三方共用

**C1.** 規則表 `spec.js` 是純資料：`ORDER`、`CLOSING_TURNS`、`ITEMS`（`up`、`jump`、`fx`、`onLevel`、`hazard`、`grip`、`delay`、`stall`，加上給演出層的自由欄位 `meta`；其他欄位結構檢查會報未知）、`AFTER_TURN`、`STORIES`、`FINALE`、`ENDINGS`、`ACCEPTANCE`、`TITLE`。引擎、求解器、演出層都讀同一份；演出層從規則層讀清單（例如 `lockFlags(spec)`），不自己複製一份。
- 每個欄位的意義與例子在 starter 的 `spec.template.js`。

**C2. 引擎介面：不可變的 `place(state, id, spec) → { state, events }`，加上 `advance(state, spec)` 跑收尾回合。**
- 事件：`placed`；`grow`（`from`、`to`、`via`＝真的讓條件成立的幫手，跳級的第二級帶 `jump: true`）；`fx`（`delta`、`lock`、`flag`、`cause`、`story`）；`stall`；`wait`（`waits[{ item, for }]`）；`after`。
- 一回合的處理順序：放置 → 放置反應（fx）→ 災害持續（hazard）→ 搗蛋（grip，先「不抓」試跑一次）→ 反覆掃描升級 → stall → wait → 回合結束反應（AFTER_TURN）。
- `SCAN_LIMIT 64`：病態規則丟出帶物品名的錯誤。
- 狀態欄位：`lv`、`age`、`held`、`locked`、`flags`、`order`、`turn`。演出層只用 `{ lv, flags }`：所有外觀都是它的純函數，所以「跳過」就是直接套最終狀態。

## 2. starter 的工具

| 指令 | 做什麼 | 什麼時候跑 |
|---|---|---|
| `npm test` | 主題中立檢查（只管 starter 本身的程式）＋所有測試：引擎語意、每個 `examples/<名稱>/` 的結構、驗收、`expected.js` 釘的值、根目錄 `spec.js` 的結構 | 每次改完 |
| `npm run check` | `node solver/run.js spec.js --check`：先跑 `validateSpec`，再全枚舉 N! 種順序，印分佈與報告，跑 `ACCEPTANCE` 驗收；失敗 exit 1 | 每次改規則 |
| `npm run stats` | 同上但不驗收 | 想看數字時 |
| `npm run tighten` | 收緊器：在 `up[]` 上逐條 AND 候選子句，讓失敗分數降到 0；**只印建議、不改檔** | 結構已對、只剩最後 1–2 條多解時（新表前期的結構問題不要用它） |
| `npm run solutions` | 劇透表 → `docs/solutions.md`：正解逐回合表（每個升級「因為誰」）、每個結局的代表順序（附 id 陣列，可以直接抄進 `expected.js`）與條數、統計、報告；保留檔案裡的「## 調參紀錄」段 | 驗收通過後、每次改規則後 |

**C3. 求解器：深度優先列舉全部 N! 種順序，共用前綴狀態。** 8 個物品 40,320 種約 1 秒。
- 驗收失敗是結構化的 `{ kind, … }`：`trueCount`（走到真結局的條數不對）、`trueEnding`（全 MAX 卻不是真結局）、`badUnreachable`、`avgMax`、`greedy`、`pacing`、`engineError`、`custom`。
- **只報告、不擋**的四項：
  - 單一順序結局：非真結局中只有 1 條順序走得到的（B26 的教訓；拿去問使用者要不要留）。
  - 死規則：從未成立的 `up`／`jump` 條件、從未發出的反應、從未立過的旗標（B22）。另列「條件成立過、但沒有因它而升級」（shadowed）：條件在某個狀態成立過，卻從沒因為它升級。多半是被跳級跨過（物品永遠從 n−2 直接跳到 n），或時機不對（只在物品不在 n−1、被鎖或被抓住、這回合已經長過時成立）。不算死規則，不一定要刪；但要確認它不是你以為會擋人或會帶動的那一條。
  - 結局集中度：最大宗結局的佔比（原作一度大多數的局結尾同一張圖的教訓）。
  - 位置可行性表：每個物品放在第 k 位時能到的最高級，對照尺度設計。

**C4. 收緊器：在 `up[]` 上逐條 AND 候選子句（別的物品的 `minLevel`／`maxLevel`、自己的 `age`），讓分數降到 0。**
- 分數權重照失敗種類（`trueCount` ×100、`trueEnding` 50、`greedy` 20、`avgMax` 超出量 ×10、`badUnreachable` 30、`pacing` 10、`engineError` 1000、`custom` 30）。權重表在 `solver/tighten.js` 檔頭。
- 只動升級條件，不碰災害、搗蛋、分岔、結局。建議的子句要**先想故事**再抄進規則表；說不出故事就不要用。
- 什麼時候用：**最後 1–2 條**的收尾。它只會在條件上補洞，不會發現「多解是因為 MAX 有餘裕」這種結構問題；新表的前期（全 MAX 十幾條）先看位置可行性報告、回第 2 步調分層。一次壓力測試裡它對一張 16 條解的新表建議了兩條子句，兩條都說不出故事，被正確地放棄了。
- 心得：光收緊救不了節奏。原作有一次救回唯一解，是「先放寬三條、再收緊三條，外加兩條門檻，每條都缺一不可」。

## 3. 寫規則資料的順序

**C6. 先算可行性，再寫內容。** 「第 k 個放的有幾個成長回合、加一次跳級最多幾級」的表，在定級數之前就算（算式見 [choices.md](choices.md) 的 B2）。
- 抓到的錯：原作第一版「沒有任何順序能全滿」；不讓剛放下的物品當回合長，總級數就排不下。

**C5. 改規則表時，先寫一份丟棄式試作表全枚舉，通過再照抄進正式檔。**
- starter 的做法：試作表放 `examples/<名稱>-try/spec.js`（或任何路徑），用 `node solver/run.js <路徑> --check` 跑，通過再搬進正式的範例資料夾。
- 規矩：「這張表就是權威：把現有的 `up`／`jump` 全部清掉換成這張表，`npm run check` 應該直接過；對不上就是引擎行為被改到了，不是表要調」。

寫規則資料時的順序（dragon-valley 就是這樣做出來的，第一次跑就一解）：
1. 物品、級數分層、可行性表。
2. 正解的逐回合表：每一回合放什麼、每個物品到幾級、誰帶動誰。
3. 從正解回推每一級的 `up`：正解那一回合場上有什麼，就要求什麼（B8），每條寫一行故事。
4. 只為正解需要的地方寫 `jump`，並把跨過的 `up[n−1]` 的阻擋寫進去（B6）。
5. 災害、搗蛋、分岔、過期、收尾考驗、結局。
6. `npm run check`，照下面的階梯調。

### 掃描順序 ORDER：同一回合誰先看到誰

`ORDER` 既是物品清單，也是引擎每回合掃描升級的順序。引擎照 `ORDER` **反覆掃到不動為止**，每個物品一回合只走一步，掃到誰就當場決定。分成兩類看：
- **不受 `ORDER` 影響：`up` 裡「至少」類的條件（`minLevel`、`present`）。** 還沒升級的物品每一輪掃描都會重看一次自己的 `up`：排在前面的第一輪沒成立，下一輪會再看，同回合 A 升了讓 B 升照樣發生。（前提是條件不會在同一回合由真變假；掃描中途有負向 `delta` 把對方打下來時例外。）
- **受 `ORDER` 影響的第一種：在發生那一刻只判定一次的事。** 之後不會因為別人晚一點才升級而重看。
  - 跳級的決定：輪到它時如果 `up[n]` 已經成立、`jump[n+1]` 還沒，就先 +1，這回合不再長；跳級要的幫手這回合晚一點才升上來，它就錯過了。
  - 反應的條件：`onLevel`／`fx` 的 `when`、分岔的 `branch.when`，在升級（或放下）那一刻判定一次。
  - 正向 `delta`：套用那一刻目標這回合長過沒有，決定它被加到幾級（連 delta 一回合最多比回合開始高 2 級）。
  - 例：dragon-valley 騎士 Lv5 的分岔看「法師 ≥6」。法師排在騎士前面，最後一回合法師先升到 6、騎士再宣誓，分岔看到 6 → 聖騎士。把 `ORDER` 換成騎士在法師前面，騎士先宣誓、看到法師還是 5 → 黑騎士，720 種順序走到真結局的變成 0 條（`test/examples.test.js` 釘著這個實驗）。分岔的條件雖然是 `minLevel`，它只判定一次，所以跟 `ORDER` 有關。
- **受 `ORDER` 影響的第二種：會在同一回合由真變假的條件：`maxLevel`、`not`、`ltPlus`、`flag … is`**（寫在 `up` 裡也一樣）。排在前面的物品先掃到，看到的是對方升級前的級數，條件成立就當場升了；排在後面的看到的是對方這回合的新級數，可能已經不成立。
- 貪婪玩家的同分取 `ORDER` 前面的，所以換 `ORDER` 也可能改變 `greedy` 的結果。

**刻意用它調時間差。** 例：災害物品排在 `ORDER` 最前面，它這回合升級（例如流星雨從 Lv2 變 Lv3、雨停了）之後，後面所有物品看到的都是新級數。如果某個物品寫了「災害還在下才能做的事」（`maxLevel: [災害, 2]`），災害排前面時那一回合就做不成了，窗口提早一回合關；排後面時窗口多開一回合。寫在 `up` 裡、用 `minLevel` 的「等災害過去」則不受影響（寫在跳級或反應的 `when` 裡就會受影響，見上面）。
- 這是脆弱的設計：`ORDER` 在畫面上看不見，之後誰加一個物品、換一下順序，解就可能變。用了就**在規則表檔頭寫明「X 排在 ORDER 第幾個，是為了哪一條條件」**，改 `ORDER` 一律重跑 `npm run check`。
- 先確認真的有作用：把它挪到別的位置跑一次 `npm run stats`。一次壓力測試裡代理把災害物品排到最前面以為擋掉了一組互換，實驗顯示挪到最後全枚舉結果完全相同（擋掉互換的其實是 `minLevel` 條件），只有貪婪的同分順序變了。

## 4. 唯一性從哪裡來

- **物品少的時候，唯一性主要來自級數分層加跳級。** dragon-valley（6 個物品）把巨龍以外的 `up` 全換成「自己長」，仍然剛好一解——因為第 k 個放的最多到 9 − k 級，只有一種排法能讓每一樣都到 MAX。
- 那條件做什麼？**控制難度（隨機平均 MAX）和讓失敗看得懂。** 同一個實驗裡平均 MAX 從 1.05 變成 3.33，饑荒結局整個消失：錯的順序不再在樞紐上連鎖停住，玩家也看不出錯在哪。
- 第二個例子（一次壓力測試，7 個物品的太空站大綱）：MAX 留餘裕（8/7/6/6/4/3/3）時全 MAX 16 條；改成頂著位置上限（9/8/7/6/4/3/3）剩 2 條，再加兩條有故事的條件剩 1 條。把災害以外的 `up` 全換成自己長，仍是 2 條、平均 MAX 4.05（有條件時 1.09）。
- 反過來說：**MAX 越貼著位置上限，唯一性越靠分層；MAX 留餘裕，唯一性就要靠條件。** 兩種都可以，前者條件少、表穩，但使用者要求降低某樣的 MAX 時唯一解會立刻壞；後者條件多、要多花力氣讓每條都有故事。
- 所以「已經一解」不代表條件可以省；看 `avgMax`、結局分佈、每個壞結局當不當得上標題，再決定。
- 收緊器只為「走到真結局的條數」加子句。對已經一解的表它回 score 0、什麼都不建議（dragon-valley 就是）。**要示範或練習收緊器，得先做一張刻意放鬆的表**（例如把一半的 `up` 改成 `{ always: true }`、拿掉跳級的條件），讓多條順序都走到真結局。

## 5. 救回唯一解的階梯

**C10. 唯一解被打破時（零解或多解），照這個順序試：**
1. **調有故事的門檻**：`minLevel`／`maxLevel` 的數字，故事跟著改（B21；dragon-valley 的巨龍門檻 ≤3 → ≤1，「乾草田一點就著、水田不怕火」）。
2. **加減條件**：加一條有故事的要求、或拿掉一條；可以參考 `npm run tighten` 的建議。
3. **最後才動級數**：改 `max` 會牽動可行性表與整張正解逐回合表。原則：優先調跳級門檻與 +1 條件，不動級數分層。
- 不要加回合來湊（B-X17），那是使用者的決定。
- **這個順序是給後期微調的。** 正解逐回合表、故事、演出都定了之後，動級數最貴，所以排最後。**設計初期**不一樣：表剛寫好、全 MAX 有很多條，而位置可行性報告顯示好幾樣的 MAX 比它在正解位置的上限低——多解多半就來自這些餘裕（見第 4 節），直接回到尺度那一步把 MAX 調到上限，往往一次就從十幾條降到一兩條，剩下的再用門檻與條件收。分辨方法：多解的那幾條順序，是不是「MAX 有餘裕的物品互換位置」。

**貪婪走得到真結局（`greedy` 失敗）。** 貪婪玩家每一步選「放完之後全場總級數最高」的物品（同分取 `ORDER` 裡排前面的）。它走得到真結局，代表正解每一步都是當下最划算的選擇，謎題太直線。
- 解法：讓正解上有一步**看起來虧**。最自然的是放下當回合不長的物品（`up[2]` 要 `{ age: [id, 1] }`），排在「別的選擇當下長得更多」的回合。災害物品最適合：放下那回合只做檢查、不長。dragon-valley 的巨龍第 5 個放就是這樣，貪婪玩家先放了別的。
- 第二種做法：在關鍵那一步讓**錯的選擇看起來更賺**。有故事地放寬另一個物品的早期條件，讓它在那一步放下時當下長得比正解的選擇多。例（一次壓力測試，太空站大綱）：流星雨已經 `age ≥ 1`，貪婪仍走得到；把通訊天線 `up[2]` 從「太陽能板 ≥7」放寬到「≥5」（有電就能先裝），第 5 步放天線當下 +2、放流星雨只 +1，貪婪就先放了天線而走偏。放寬之後要確認仍然一解（放寬的條件可能讓別的順序也長滿）。
- 讓它「看起來虧」的那一步，也要在可行性表上重算（放下當回合不長 = 少 1 級）。
- 物品很少（4–5 個）時這條特別容易失敗；改了之後仍過不了，把 `greedyMustFail` 要不要放寬拿去問使用者。
- 不要為了騙貪婪去加正解用不到的跳級（違反「只留正解需要的跳級」）。

**壞結局成立過、卻當不了標題。** `everyBadReachable` 看 `satisfied`（被前面的結局遮住也算到得了），所以驗收會過；但 `npm run check` 的結局分佈（resolve）裡沒有它、劇透表寫「0 種」，玩家永遠看不到這個畫面。處理跟死規則一樣（B22）：
- 調它或遮住它的那個結局的門檻（故事一起改）；
- 調 `ENDINGS` 的順序（時間上先發生的排前面）；
- 都不行就拿掉。

**C9. 用全枚舉抓死規則和到不了的結局。**
- 實例：原作有一個壞結局的門檻太緊、永遠到不了，放寬之後雖然成立過，卻在 40,320 種順序裡一次都當不了標題，整條刪掉。預設跳級上線後有兩條跳級一次都不發生。
- 驗收的「每個壞結局都至少一條順序成立」是這類問題的哨兵；「成立但當不了標題」要看 `npm run check` 印的分佈（resolve）。

## 6. 釘住結果

**C7. 每次改規則都重跑分佈，把數字寫回 spec 的檔頭註解留紀錄，再重產劇透表。**

**C8. 每個結局釘一條代表順序，寫成字面值，測試重算。**
- starter 的做法：遊戲的規則表放在 `examples/<名稱>/spec.js`，同一個資料夾的 `expected.js` 寫 `TOTAL`、`SOLUTION`（`ACCEPTANCE.trueEndings` 不是 1 時改寫 `SOLUTIONS`：全部正解的陣列，照全枚舉的先後）、`DISTRIBUTION`、`REPRESENTATIVE`（每個出現過的結局一條，用劇透表列的代表順序）、`REPORTS`，可選 `NOTABLE`（其他值得釘的順序，例如示範災害持續的那條）。格式照 `examples/dragon-valley/expected.js`。
- `npm test` 會重算；規則一改、數字對不上就失敗，逼你重釘。
- 還沒寫 `expected.js` 的範例只跑結構檢查（驗收看 `npm run check`；驗收與釘值的測試標成略過），所以設計中途 `npm test` 不會因為沒釘或驗收還沒過而紅。skill 自帶的範例例外：在 skill 資料夾裡跑時，它們少了 `expected.js` 會直接失敗。
- **複製出來的 starter 裡 `npm test` 的 skipped 從哪來**：`test/skill.test.js` 的 8 項 skill 文件檢查（上一層沒有 SKILL.md 就整檔略過）；每個沒有 `expected.js` 的範例 4 項（全枚舉結果、驗收、報告、代表順序）。例：一個已釘好的遊戲 → skipped 8；一個還沒釘的 → skipped 12。

**C18. 裁決帳本：所有執行中的決定都編號記下。**
- 每條附日期、使用者怎麼說、數字；被取代的段落註明「由某某取代」。starter 的劇透表有「## 調參紀錄」段會被保留，可以記在那裡；或用 `templates/rules-design.md` 的裁決帳本段。
- 每批做完寫一份紀錄：做了什麼、使用者還沒看的、延後的小問題。

## 7. 引擎語意上踩過的坑（starter 的測試都有涵蓋）

**C11.**
- 跳級繞過阻擋（B6）。
- 跳級的 `via` 順序：先列第一級的幫手，不然演出會「第二級的幫手跑來敲第一級的門」。
- 抓了又當回合放過：加「不抓試跑」。
- 降級後同回合又升級：加 `knocked`。
- 災害看回合開始的級數，不是掃描中途的級數。
- 正 delta 可以讓物品繞過升級條件（被加上去的那一級不看它自己的 `up`）——盡量不要用正 delta。
- 一條反應同時有 `grip` 和 `flag` 時，事件上的 `flag` 會被覆蓋（已知行為，starter 沒改）：兩件事分成兩條反應寫。

## 8. 跟使用者合作

**C15. 每批做完附一份「給使用者看的清單」；使用者用錄影或截圖回饋，逐幀查明再改。**
- 誤判實例：「某棟升級兩次」其實是別人的 LEVEL UP 冒在它上方；「某棟閃一下」是 0.4 s 的起因光；「卡頓」是第一次出現時才載模型。
- 錄影檔名要核對修改時間。

**C16. 「規則說 X，畫面演 Y」要當成 bug。** 例：規則判定的是某個壞結局，畫面卻只演了收尾考驗被帶偏（那個結局還沒有自己的收尾）。

**使用者不在場時：寫下問題、帶著假設往前做。** 背景執行或只拿到大綱時，「一定要問」的裁決（難度、語氣禁區、降級、壞結局數量……）不能卡住整個流程，也不能悄悄替使用者決定。每個問題寫成「問題＋先採用的假設＋理由」（例：「隨機平均 MAX 要多少？假設 ≤ 1.2，因為大綱說休閒玩家但沒給數字；實測 1.09」），照假設做完，收進 `templates/rules-design.md` 的「待使用者確認」一節，交付時放在最前面。使用者回答後記進裁決帳本；推翻了假設就照第 5 節重調。

**C20. 不要把使用者對某一個機制的「可以參考」推廣到所有地方。** 原作曾把「GROW 的不升級可以參考」擴大成「每一級都要觸發者」，整批重做（B-X3）。不確定範圍就問。

**C21. 用反目標的數字當警報，但要承認被推翻過。** 新專案要嘛把反目標寫進 `ACCEPTANCE.custom`，要嘛明文作廢。

**C22. 目標沒達成時記帳接受，不偷砍使用者沒點名的東西。** 例：最後一輪目標 ≤ 45 s，實際 48.0 s，剩下的都是使用者沒點名的，留給下一輪裁決。

**C19. 先研究 GROW 再設計演出。** 原作逐秒看了 GROW 三款的影片，整理出共通規則；先做一個回合的試作給使用者確認方向，再全面重做。

## 9. 演出層的量測（交給演出層之後）

這些是原作演出層的工具，starter 沒有；新專案做演出層時參考。

**C12. 節奏工具：無頭跑完整局演出，量每一回合的秒數。** 固定種子；跑正解加每個結局的代表順序。門檻起點見 [presentation.md](presentation.md) 的 D7。

**C13. 時間會變動的東西（例如列車在環上的位置）要掃多個起點，量最壞情況。**

**C14. 預算也是驗收。** 可見人數、draw call、骨架角色數、程式大小都訂上限；預算逼出取捨。

**C17. 結局的可讀性要在手機截圖上確認，而且要迭代。** 原作有一個結局改了三版，都是看手機截圖才發現問題。
